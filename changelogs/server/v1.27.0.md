### Added

- **Open a workspace together with others, in one step**: A new button next to the workspace switcher lists the other workspaces. Pick one or more and "Open together": you land in Overview, in the group that holds exactly those workspaces, created and named after them ("jean2 + db-web") when there was none. Every session tab you had open comes along, with the same one in front. The way back keeps its tabs too: leaving Overview for a workspace, by the header toggle, the shortcut or the switcher, lands in the workspace of the session in front with that workspace's open tabs still open. And going from a workspace to Overview keeps its tabs when the active group holds that workspace.

- **MCP tools load on demand in Prokop sessions**: A workspace with more than ten MCP tools used to send every one of them, schema and all, on every step. Now the agent sees one `tool_search` tool with the deferred tools listed by name and server; it loads the ones it needs by name or by keyword, and those stay callable for the rest of the session. The built-in tools (delegation, messaging, group chat, visuals) are never deferred. Claude Code and Codex sessions already worked this way.

- **Move files and folders in the Explorer**: Drag an entry onto a folder, or onto the empty space below the tree for the workspace root, and it moves there. The row's menu has "Move to…", which asks for the destination folder and offers the folders matching what you type. A move the server refuses puts the entry back where it was and says why. Open editors follow a moved file.

- **On the phone a group chat is a tab next to your sessions**: It used to open as a separate screen with a back arrow, like the file views. It now sits in the Chat tab strip with the sessions, and tapping a session or a group switches between them. On a narrow screen the members sit on their own row under the group's name instead of spilling over the thread. In any width the row shows the members that fit, the ones that need you and the working ones first, and folds the rest into a "+N" chip whose menu lists them with their status and the same actions.

- **Posting to a group and stopping its members feel as quick as in a session**: Your post shows in the thread and leaves the message box the moment you send it, before the server has woken the members; a post the server refuses is taken out again and your text put back. A stopped member reads idle at once instead of after its turn has wound down.

- **A member's reply shows in the group as it is written, without opening its session**: The group only showed a member's reply live, and only counted it as working, when its hidden session had been opened in a pane. The group now keeps the member's streamed reply on its own.

- **Stop a group's members from the group**: While members work and nothing is typed, the group's send button is Stop and interrupts every working member, as does double Escape with the group in front. A single member stops from its chip's menu.

- **Escape focuses the group chat's message box**: With a group in front, the focus-input shortcut used to jump to the last session you had focused, switching tabs on the way. It now focuses the group's own message box, and the session behavior is unchanged when a session is in front.

- **Group chat with your agents**: A group is one shared thread between you and 2 to 10 of your agents in a workspace. Groups sit in the sidebar under the sessions; the plus in that header makes one (name, members from your agents, default member), a row's menu edits or deletes it, and a group opens as a tab in the center like a pull requests view. In the group, each message shows its author (you, or a member in its own color), a member's tool calls read as one summary row each, a handoff is one line naming both members, and joins and leaves are notes. The header shows every member with what it is doing (working, needs you) and a menu to open its hidden session, make it the default, or remove it. Typing `@` in the message box lists the members and everyone; a picked member becomes a chip, so who answers is explicit, and a message that mentions nobody says who it will go to. Typing `/` lists your prompts as in a session: `/review @Reviewer the queue` sends the review prompt with the rest filled in, to Reviewer. While a group is on screen, a member's reply shows up as it is written, and members' approvals and questions are answered right there, under the thread. The permission shield in the group's message box is one setting for the whole group: every member runs with it, a change applies to all of them at once, and a member added later gets it too. Routing: you @mention who should answer (`@Name`, `@everyone`, or the chips), and a message that names nobody goes to the group's default member. Each member answers from its own hidden session on its own harness and model, so Prokop, Claude Code and Codex agents sit in the same group. A woken member receives everything said since it last spoke, each line labeled with its author (`[User]` for you), the roster the first time and after a membership change, never its own messages; long gaps are capped at the newest 50 messages or 20,000 characters with a count of what was left out, and `group_history` reads the rest. A member's finished reply is posted to the group as that member, with its text in full and each tool call as one summary line; the full tool cards stay in the member session. `handoff_to_agent` passes a distinct next stage to another member: it posts a visible handoff and wakes that member one hop further, with the same six-hop limit as agent messages; handing off to yourself or to a non-member is refused. Joins and leaves are posted as system lines. Deleting a group stops and deletes its member sessions. Member sessions stay out of every session list; the group is the one place to see them. The HTTP API is `/api/groups` and `/api/workspaces/:id/groups`, with members and messages under a group, and the server sends `group.updated`, `group.deleted` and `group.message.created` so every client follows along without polling.

- **Agents message each other**: An agent can send another of your agents a request, a question, a status, a result or an FYI with the new `message_agent` tool, available on Prokop, Claude Code and Codex like the delegation tools. The recipient works on it as itself, in a conversation session in its own home, with its own instructions, memory and skills, and the conversation keeps its context across messages from the same sender session. Delivery is asynchronous: the sender keeps working, and for a request or a question the recipient's final answer comes back to the sender as a new message when its turn ends; a failed turn returns its error instead of silence. Incoming messages show as a line naming the agent and the intent, with the agent's name opening the conversation. An agent accepts messages only when its definition says `acceptsMessages: true`, and only agents with a home can; `canMessage` limits whom an agent may write to, like `canSpawnSubagents`. Messages stop after six hops from your own turn (`AGENT_MESSAGE_MAX_HOPS`). Deleting the session that started a conversation deletes that conversation in the recipient's home; archiving keeps it. Conversations count as the recipient's own work for learning, not yours. In the sender's transcript the call shows the recipient, the message and the intent, opens the conversation, and says "working" while the recipient runs or "needs you" while it waits on an approval there. In the recipient's home, conversations other agents started sit folded under "From other agents" in the sidebar. Agent settings get a Messaging section: whether other agents may write to this agent, and which agents it may write to.

- **Notes from background work look like notes, not like your messages**: When a background command finishes, or a delegated task finishes or needs an answer, the agent is woken with a message. That message used to show as one of yours, in your bubble, with edit and revert. It now shows as a single muted line under the conversation: the command or the task, how it ended (exit code and duration for a command, harness and model for a task), the output as a terminal chip, and the task's name opens its session. A long result folds behind Show. The same line appears when the note waits in the queue behind a running turn. Copying it or finding it in the prompt map gives the readable sentence, not the marker.

- **Hand implementation work to sessions in their own worktrees**: From one conversation an agent can start top-level sessions, each on a new branch in a new managed worktree with the repository's setup applied, and keep talking to you while they work. These are ordinary sessions: open one, continue the conversation there, review the diff and merge. The agent is told when each finishes, with the branch, the worktree and the number of changed files, and when one needs an answer. Subagents never get their own worktree; this is for work that should become a branch. Three such sessions can run from one conversation at a time (`DELEGATION_MAX_LAUNCHES`). Deleting a launched session leaves its branch and worktree alone. A top-level session does not have to get a worktree: with `isolation: "checkout"` the agent starts one in the current checkout, sharing the working tree, under the same approval setting and cap.

- **The agent asks before picking a model, a harness, or starting worktree sessions**: A new agent's delegation targets default to "Ask me each time": when it wants to run a role on a harness or model other than the role's own, you get a question where you are, with Allow once, Allow for this agent (which remembers the harness in its settings), or Deny. A role run as configured never asks. Starting sessions in new worktrees asks too, listing branch, base, harness and model, unless the agent's new "New sessions" setting says start without asking or never. Agents you already have keep their current behavior.

- **Delegated tasks survive retries and restarts**: A delegation carries an optional `clientRequestId`; a retried call with the same id returns the task it already started instead of a second subagent, running or finished. Each task is recorded, so a result that finished just as the server stopped is delivered to the parent when the server comes back.

- **One delegation tool on every harness**: Prokop, Claude Code and Codex sessions all get the same `delegate_task`, `delegation_capabilities`, `task_status` and `task_cancel`: hand a task to a role you defined, on its own harness and model or on ones the agent picks, and get its result back. Prokop's `task` tool is gone; `delegate_task` is its subagent tool now. The tools come with the workspace tools, like the browser tools, and are not an MCP server to configure: an agent has them when it may spawn subagents, whatever its mode. A delegated task now returns at once by default on every harness and its result arrives later as a message, so a Prokop agent ends its turn after delegating and reports when the result lands; `mode: "wait"` still blocks for it. Claude Code and Codex keep their native subagents for same-model work, and the instructions say which to use when. When a delegation needs your yes (a harness or model the agent may not pick alone, a new worktree), the question shows on the session you are looking at, on every harness, and "Allow for this agent" remembers the harness for that agent. In standard mode you are asked; extended and full mode approve a harness or model change on their own. A child's question or approval shows there too. In the transcript a delegation reads the same on every harness: the row is named `delegate_task`, shows the task and whether it is running, waiting on you or finished, and opens the child session; old `task` rows keep their link. In agent settings, delegation (roles, targets, launches) is its own section, since it applies on every harness; the Prokop runtime section keeps the tool list and temperature.

- **Subagent roles get MCP tools**: An agent in subagent mode used to get no MCP servers or built-in tools at all. It now gets the same ones as a primary agent; its own settings decide what it may do.

- **Delegate without waiting**: The task tool takes `mode: "async"`: the call returns at once and the subagent's result arrives in the parent session as a new message when it finishes, so the agent keeps working meanwhile. A waiting call that passes its timeout (ten minutes by default) or whose subagent stops for a question or approval returns the same way, and the task carries on; it is never cancelled by a timeout and the agent is never asked to poll. A question or approval from a subagent, including one running on Claude Code or Codex, now shows up on the session you are looking at, and a subagent that waits for an answer wakes its parent with a note. A subagent interrupted by a server restart is reported to its parent once and never restarted on its own.

- **Pick a harness and model when delegating**: Every delegation names a role, which runs on its own harness and model, or on the agent's when it sets none. The task tool takes a `target` that overrides that for one task: the harness (Prokop, Codex, Claude Code), model and effort a subagent should run on. Each agent has a new "Delegation targets" setting that says whether it may: any enabled harness, ask each time, roles only (every role runs exactly as configured), or specific harnesses without asking. A new `delegation_capabilities` tool shows the agent its roles with their defaults, the harnesses enabled on this machine with a short model list each, and the limits. Each CLI model lists its reasoning efforts and the default one, each Prokop model its variants, and `target.variant` picks one for a task (the `delegate_task` schema names the efforts each CLI offers); a child that inherits the parent's model inherits its effort too. Refusals come back with a reason code: a disabled or missing harness, an unknown model, a forbidden override, depth, or too many running subagents under one session (eight by default, `DELEGATION_MAX_CHILDREN`). A child never gets a wider permission mode than its parent.

- **Subagents on Claude Code or Codex**: A subagent role whose model is pinned to Claude Code or Codex now runs there when a Prokop session delegates to it. The child session belongs to that harness from the start, shows up live like any subagent, uses the role's pinned model or the CLI default, and hands its final answer back in the usual task result. Stopping the parent stops the child. A role with no pin keeps running in Prokop as before.

- **Worktree setup from a repository file**: A repository can describe how a new managed worktree gets ready in `.prokop/worktree.json` at its root. When a worktree is created, ignored files such as `.env` are copied from the main checkout, directories such as `node_modules` are cloned without taking extra disk space, and env and template files are written with a port block reserved for that worktree (`{{port}}`, `{{port+1}}`) and a unique key for database or topic names (`{{key}}`). Every target has to be in `.gitignore`, so the worktree stays clean and can still be removed; a target that is not is refused with the path to add. The file is read from the main checkout and checked before the worktree is created, so a typo refuses creation with the line that is wrong. Each worktree reports its setup state and port block.

- **Setup commands run in the background**: The `setup` commands from `.prokop/worktree.json` (for example `bun install` or creating a database) run in the new worktree after it is created, through your login shell, with the file's env values and the worktree's port, name, key and paths in the environment. Because commands come from the repository, they run only after you approve them once per repository; a changed file asks again. The worktree is usable while they run, output goes to a log per worktree, and a failed command reports the step and the last lines of output. Retry and re-run are explicit; a server restart during setup leaves it marked as interrupted and never reruns it by itself.

- **Setup on the worktree row**: Each worktree in the Worktrees panel shows where its setup stands on one line: the running step with a spinner, the commands with a Run setup action while they wait for approval, the failing step with Retry and Log after a failure, the reserved port once ready. The log opens in a dialog and follows the setup as it moves from step to step. The session checkout menu and the checkout strip under the input mark a worktree whose setup is still running, pending or failed.

- **Agents know about worktree setup**: A session working in a worktree whose setup is still running, waiting for approval, or failed gets one note at the start of its turn saying so, on every harness, so the agent waits or tells you instead of running its own install. The worktree also carries a small `.prokop/setup/state` file (`pending`, `running`, `done` or `failed` with the output tail) that any tool can read; it is ignored by Git and never makes the worktree dirty.

- **Teardown before removal**: Removing a worktree stops a setup that is still running, then runs the file's `teardown` commands (dropping a database, for example) before the directory goes. A failing teardown does not keep the worktree around; the removal goes through and the worktree's last state shows a warning with the output. Purging a removed worktree also deletes its setup log and frees its port block.

### Fixed

- **Claude Code compaction no longer locks the conversation**: Compacting a long Claude Code session could take longer than the two minutes Prokop waited, so it was cut off and the conversation refused every message after it. Compaction now gets ten minutes. A compaction that still ends without a clear outcome (cut off, or the server restarted) is checked against Claude Code's own history the next time you send or compact: if nothing changed, the conversation carries on; if it did compact, that is recorded. It stays locked only when that history cannot be read.

- **Claude Code turns no longer fail with "Unknown Claude content block"**: Replies that used a server-side tool (such as the advisor or web search) ended in that error and left the conversation stuck. Prokop now skips those parts and keeps the rest of the reply.

- **Stopping a parent now stops its delegated Prokop subagents**: Once a delegated task ran on after its parent stopped waiting, Stop on the parent, Stop on the child and `task_cancel` only marked the child as interrupted while it kept calling tools, with no control left to stop it. The child's run is now registered with the interrupt manager for its whole life, so all three end it; the parent gets a note that the task was interrupted instead of whatever text the child had produced so far.

- **Stop a subagent from its own session**: Opening a running subagent used to show a read-only note and, for Prokop and Claude Code children, no way to stop it. While a subagent the host drives is working, that bar now says so and carries a Stop control; it reads "Stopping" until the server confirms, then turns into the read-only note. A Claude Code agent thread that lives inside its parent's process still has no Stop of its own.

- **The arrow keys visibly move through file and prompt suggestions again**: The row picked with the arrows in the `@` file list, the `/` prompt list, the group's member list and the folder picker was drawn in a color almost identical to the list behind it in dark themes. It now carries the same tint as selected text.
