### Added

- **Worktree setup from a repository file**: A repository can describe how a new managed worktree gets ready in `.prokop/worktree.json` at its root. When a worktree is created, ignored files such as `.env` are copied from the main checkout, directories such as `node_modules` are cloned without taking extra disk space, and env and template files are written with a port block reserved for that worktree (`{{port}}`, `{{port+1}}`) and a unique key for database or topic names (`{{key}}`). Every target has to be in `.gitignore`, so the worktree stays clean and can still be removed; a target that is not is refused with the path to add. The file is read from the main checkout and checked before the worktree is created, so a typo refuses creation with the line that is wrong. Each worktree reports its setup state and port block.

- **Setup commands run in the background**: The `setup` commands from `.prokop/worktree.json` (for example `bun install` or creating a database) run in the new worktree after it is created, through your login shell, with the file's env values and the worktree's port, name, key and paths in the environment. Because commands come from the repository, they run only after you approve them once per repository; a changed file asks again. The worktree is usable while they run, output goes to a log per worktree, and a failed command reports the step and the last lines of output. Retry and re-run are explicit; a server restart during setup leaves it marked as interrupted and never reruns it by itself.

- **Setup on the worktree row**: Each worktree in the Worktrees panel shows where its setup stands on one line: the running step with a spinner, the commands with a Run setup action while they wait for approval, the failing step with Retry and Log after a failure, the reserved port once ready. The log opens in a dialog and follows the setup as it moves from step to step. The session checkout menu and the checkout strip under the input mark a worktree whose setup is still running, pending or failed.

- **Teardown before removal**: Removing a worktree stops a setup that is still running, then runs the file's `teardown` commands (dropping a database, for example) before the directory goes. A failing teardown does not keep the worktree around; the removal goes through and the worktree's last state shows a warning with the output. Purging a removed worktree also deletes its setup log and frees its port block.
