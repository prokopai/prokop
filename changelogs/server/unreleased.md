### Added

- **Hand implementation work to sessions in their own worktrees**: From one conversation an agent can start top-level sessions, each on a new branch in a new managed worktree with the repository's setup applied, and keep talking to you while they work. These are ordinary sessions: open one, continue the conversation there, review the diff and merge. The agent is told when each finishes, with the branch, the worktree and the number of changed files, and when one needs an answer. Subagents never get their own worktree; this is for work that should become a branch. Three such sessions can run from one conversation at a time (`DELEGATION_MAX_LAUNCHES`). Deleting a launched session leaves its branch and worktree alone. A top-level session does not have to get a worktree: with `isolation: "checkout"` the agent starts one in the current checkout, sharing the working tree, under the same approval setting and cap.

- **The agent asks before picking a model, a harness, or starting worktree sessions**: A new agent's delegation targets default to "Ask me each time": when it wants to run a role on a harness or model other than the role's own, you get a question where you are, with Allow once, Allow for this agent (which remembers the harness in its settings), or Deny. A role run as configured never asks. Starting sessions in new worktrees asks too, listing branch, base, harness and model, unless the agent's new "New sessions" setting says start without asking or never. Agents you already have keep their current behavior.

- **Delegated tasks survive retries and restarts**: A delegation carries an optional `clientRequestId`; a retried call with the same id returns the task it already started instead of a second subagent, running or finished. Each task is recorded, so a result that finished just as the server stopped is delivered to the parent when the server comes back.

- **One delegation tool on every harness**: Prokop, Claude Code and Codex sessions all get the same `delegate_task`, `delegation_capabilities`, `task_status` and `task_cancel`: hand a task to a role you defined, on its own harness and model or on ones the agent picks, and get its result back. Prokop's `task` tool is gone; `delegate_task` is its subagent tool now. The tools come with the workspace tools, like the browser tools, and are not an MCP server to configure: an agent has them when it may spawn subagents, whatever its mode. A delegated task now returns at once by default on every harness and its result arrives later as a message, so a Prokop agent ends its turn after delegating and reports when the result lands; `mode: "wait"` still blocks for it. Claude Code and Codex keep their native subagents for same-model work, and the instructions say which to use when. When a delegation needs your yes (a harness or model the agent may not pick alone, a new worktree), the question shows on the session you are looking at, on every harness, and "Allow for this agent" remembers the harness for that agent. In standard mode you are asked; extended and full mode approve a harness or model change on their own. A child's question or approval shows there too. In the transcript a delegation reads the same on every harness: the row is named `delegate_task`, shows the task and whether it is running, waiting on you or finished, and opens the child session; old `task` rows keep their link. In agent settings, delegation (roles, targets, launches) is its own section, since it applies on every harness; the Prokop runtime section keeps the tool list and temperature.

- **Subagent roles get MCP tools**: An agent in subagent mode used to get no MCP servers or built-in tools at all. It now gets the same ones as a primary agent; its own settings decide what it may do.

- **Delegate without waiting**: The task tool takes `mode: "async"`: the call returns at once and the subagent's result arrives in the parent session as a new message when it finishes, so the agent keeps working meanwhile. A waiting call that passes its timeout (ten minutes by default) or whose subagent stops for a question or approval returns the same way, and the task carries on; it is never cancelled by a timeout and the agent is never asked to poll. A question or approval from a subagent, including one running on Claude Code or Codex, now shows up on the session you are looking at, and a subagent that waits for an answer wakes its parent with a note. A subagent interrupted by a server restart is reported to its parent once and never restarted on its own.

- **Pick a harness and model when delegating**: Every delegation names a role, which runs on its own harness and model, or on the agent's when it sets none. The task tool takes a `target` that overrides that for one task: the harness (Prokop, Codex, Claude Code), model and effort a subagent should run on. Each agent has a new "Delegation targets" setting that says whether it may: any enabled harness, ask each time, roles only (every role runs exactly as configured), or specific harnesses without asking. A new `delegation_capabilities` tool shows the agent its roles with their defaults, the harnesses enabled on this machine with a short model list each, and the limits. Each CLI model lists its reasoning efforts and the default one, each Prokop model its variants, and `target.variant` picks one for a task (the `delegate_task` schema names the efforts each CLI offers); a child that inherits the parent's model inherits its effort too. Refusals come back with a reason code: a disabled or missing harness, an unknown model, a forbidden override, depth, or too many running subagents under one session (eight by default, `DELEGATION_MAX_CHILDREN`). A child never gets a wider permission mode than its parent.

- **Subagents on Claude Code or Codex**: A subagent role whose model is pinned to Claude Code or Codex now runs there when a Prokop session delegates to it. The child session belongs to that harness from the start, shows up live like any subagent, uses the role's pinned model or the CLI default, and hands its final answer back in the usual task result. Stopping the parent stops the child. A role with no pin keeps running in Prokop as before.

- **Worktree setup from a repository file**: A repository can describe how a new managed worktree gets ready in `.prokop/worktree.json` at its root. When a worktree is created, ignored files such as `.env` are copied from the main checkout, directories such as `node_modules` are cloned without taking extra disk space, and env and template files are written with a port block reserved for that worktree (`{{port}}`, `{{port+1}}`) and a unique key for database or topic names (`{{key}}`). Every target has to be in `.gitignore`, so the worktree stays clean and can still be removed; a target that is not is refused with the path to add. The file is read from the main checkout and checked before the worktree is created, so a typo refuses creation with the line that is wrong. Each worktree reports its setup state and port block.

- **Setup commands run in the background**: The `setup` commands from `.prokop/worktree.json` (for example `bun install` or creating a database) run in the new worktree after it is created, through your login shell, with the file's env values and the worktree's port, name, key and paths in the environment. Because commands come from the repository, they run only after you approve them once per repository; a changed file asks again. The worktree is usable while they run, output goes to a log per worktree, and a failed command reports the step and the last lines of output. Retry and re-run are explicit; a server restart during setup leaves it marked as interrupted and never reruns it by itself.

- **Setup on the worktree row**: Each worktree in the Worktrees panel shows where its setup stands on one line: the running step with a spinner, the commands with a Run setup action while they wait for approval, the failing step with Retry and Log after a failure, the reserved port once ready. The log opens in a dialog and follows the setup as it moves from step to step. The session checkout menu and the checkout strip under the input mark a worktree whose setup is still running, pending or failed.

- **Agents know about worktree setup**: A session working in a worktree whose setup is still running, waiting for approval, or failed gets one note at the start of its turn saying so, on every harness, so the agent waits or tells you instead of running its own install. The worktree also carries a small `.prokop/setup/state` file (`pending`, `running`, `done` or `failed` with the output tail) that any tool can read; it is ignored by Git and never makes the worktree dirty.

- **Teardown before removal**: Removing a worktree stops a setup that is still running, then runs the file's `teardown` commands (dropping a database, for example) before the directory goes. A failing teardown does not keep the worktree around; the removal goes through and the worktree's last state shows a warning with the output. Purging a removed worktree also deletes its setup log and frees its port block.
