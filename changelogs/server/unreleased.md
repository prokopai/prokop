### Added

- **Delegated tasks survive retries and restarts**: A delegation carries an optional `clientRequestId`; a retried call with the same id returns the task it already started instead of a second subagent, running or finished. Each task is recorded, so a result that finished just as the server stopped is delivered to the parent when the server comes back.

- **Claude Code and Codex sessions can delegate too**: A session running on Claude Code or Codex gets `delegate_task`, `delegation_capabilities`, `task_status` and `task_cancel`, the same delegation a Prokop session has (where the first is still called `task`, and `task_status` and `task_cancel` are new): hand a task to a child on any enabled harness and model, or to a role you defined, and get its result back. Their own native subagents stay for same-harness work, and the instructions say which to use when. For these sessions a delegated task returns at once by default and its result arrives later as a message. A child's question or approval shows on the session you are looking at.

- **Delegate without waiting**: The task tool takes `mode: "async"`: the call returns at once and the subagent's result arrives in the parent session as a new message when it finishes, so the agent keeps working meanwhile. A waiting call that passes its timeout (ten minutes by default) or whose subagent stops for a question or approval returns the same way, and the task carries on; it is never cancelled by a timeout and the agent is never asked to poll. A question or approval from a subagent, including one running on Claude Code or Codex, now shows up on the session you are looking at, and a subagent that waits for an answer wakes its parent with a note. A subagent interrupted by a server restart is reported to its parent once and never restarted on its own.

- **Pick a harness and model when delegating**: The task tool takes a `target`: the harness (Prokop, Codex, Claude Code) and model a subagent should run on. A role pinned to a harness or model always runs there and refuses a target that says otherwise. A role without a pin takes the target, and with no role at all the agent sends a copy of its own role to the target. Each agent has a new "Delegation targets" setting that limits where it may send tasks without a role: any enabled harness, roles only, or specific harnesses. A new `delegation_capabilities` tool shows the agent its roles with their pins, the harnesses enabled on this machine with a short model list each, and the limits. Refusals come back with a reason code: a disabled or missing harness, an unknown model, a conflicting pin, a forbidden target, depth, or too many running subagents under one session (four by default). A child never gets a wider permission mode than its parent.

- **Subagents on Claude Code or Codex**: A subagent role whose model is pinned to Claude Code or Codex now runs there when a Prokop session delegates to it. The child session belongs to that harness from the start, shows up live like any subagent, uses the role's pinned model or the CLI default, and hands its final answer back in the usual task result. Stopping the parent stops the child. A role with no pin keeps running in Prokop as before.

- **Worktree setup from a repository file**: A repository can describe how a new managed worktree gets ready in `.prokop/worktree.json` at its root. When a worktree is created, ignored files such as `.env` are copied from the main checkout, directories such as `node_modules` are cloned without taking extra disk space, and env and template files are written with a port block reserved for that worktree (`{{port}}`, `{{port+1}}`) and a unique key for database or topic names (`{{key}}`). Every target has to be in `.gitignore`, so the worktree stays clean and can still be removed; a target that is not is refused with the path to add. The file is read from the main checkout and checked before the worktree is created, so a typo refuses creation with the line that is wrong. Each worktree reports its setup state and port block.

- **Setup commands run in the background**: The `setup` commands from `.prokop/worktree.json` (for example `bun install` or creating a database) run in the new worktree after it is created, through your login shell, with the file's env values and the worktree's port, name, key and paths in the environment. Because commands come from the repository, they run only after you approve them once per repository; a changed file asks again. The worktree is usable while they run, output goes to a log per worktree, and a failed command reports the step and the last lines of output. Retry and re-run are explicit; a server restart during setup leaves it marked as interrupted and never reruns it by itself.

- **Setup on the worktree row**: Each worktree in the Worktrees panel shows where its setup stands on one line: the running step with a spinner, the commands with a Run setup action while they wait for approval, the failing step with Retry and Log after a failure, the reserved port once ready. The log opens in a dialog and follows the setup as it moves from step to step. The session checkout menu and the checkout strip under the input mark a worktree whose setup is still running, pending or failed.

- **Agents know about worktree setup**: A session working in a worktree whose setup is still running, waiting for approval, or failed gets one note at the start of its turn saying so, on every harness, so the agent waits or tells you instead of running its own install. The worktree also carries a small `.prokop/setup/state` file (`pending`, `running`, `done` or `failed` with the output tail) that any tool can read; it is ignored by Git and never makes the worktree dirty.

- **Teardown before removal**: Removing a worktree stops a setup that is still running, then runs the file's `teardown` commands (dropping a database, for example) before the directory goes. A failing teardown does not keep the worktree around; the removal goes through and the worktree's last state shows a warning with the output. Purging a removed worktree also deletes its setup log and frees its port block.
